ado-dad mobile · sell flow · v2 proposal

Post an ad, photo-first

Redesign of the four add_*_form.dart screens. Photos move to step 1 and upload in the background while the seller fills in details, so "Post" is instant instead of waiting on S3.

Flutter · go_router · bloc 4 categories, 1 shell wireframe · not final visual

Today · 3 steps, upload on submit

0Category list→ 1Details (18+ fields)→ 2Photos + Video→ 3Review→ ⏳S3 upload × N, then POST

Problems: seller types everything before seeing whether photos work; all images upload serially on "Post" (long spinner, silent failure if one URL is null); a validation error on submit jumps back to step 0; the 3-step shell is duplicated in 4 files (~7k lines).

Proposed · photos first, upload as you go

0Category sheet→ 1Photos→ 2Details→ 3Price & location→ 4Review → POST

Wins: photos (the highest-effort, highest-value input) are captured while motivation is highest; uploads finish during steps 2–4 so Post is one API call; per-step validation; one shared PostAdShell with category-specific field sections plugged in.

Implementation plan

Ordered so each step ships on its own without breaking the current forms.

1 · Extract the shell

  • New lib/features/sell/ui/post_ad_shell.dart: app bar, step header/progress, step nav, draft save. Owns _step.
  • Steps as a List<PostAdStep> = [PhotoStep, detailsSection, PriceLocationStep, ReviewStep].
  • Each step implements bool validate() so "Continue" validates only that step.

2 · Media upload cubit

  • MediaUploadCubit in features/sell/bloc/media_upload/; state = list of MediaItem(localId, bytes, status: queued|uploading|done|failed, progress, url) + optional video item.
  • Starts upload on add; concurrency 3; retry per item; reorder/remove/setCover events.
  • Provided at the shell level so it survives step changes. AddPostBloc stays as-is; postAd just reads urls from the cubit.

3 · Per-category detail sections

  • Move the field code out of each add_*_form.dart (lines ~322–757 in private vehicle) into *_details_section.dart.
  • Keep the existing manufacturer/model/variant/fuel/transmission blocs untouched.
  • Section returns Map<String,dynamic> merged with price/location/media into the same payload the API expects today — no backend change.

4 · Category sheet + drafts

  • item_category.dart → bottom sheet on Sell tab; tablet keeps a page.
  • Draft = serialised form map + local media paths in SharedPreferences/Hive keyed by category; "Save draft" and auto-save on back.

5 · Reuse for edit

  • edit_add_details/*_form_edit.dart use the same shell with initialData; existing image urls seed the cubit as done items.
  • Deletes image_picker_widget.dart / video_picker_widget.dart duplicates.

Open questions

  • Max photos: 10? Current code has no cap.
  • Does the backend moderate before publish (affects screen 06)?
  • Price hint endpoint — worth doing now or later?
  • Keep video on step 1 (as drawn) or make it a separate optional step?
